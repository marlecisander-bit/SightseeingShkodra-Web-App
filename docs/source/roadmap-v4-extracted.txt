1. What we're building
Replace the current WordPress site, separate ticketing experience and standalone live-tracking app with one owned platform:
Customer app - travel-guide content, product/tour pages, booking and an embedded live map in one coherent funnel.
Admin panel - manages products, departures, content, bookings, customers, integrations and the live map in manage mode.
Booking API - owns availability, pricing, capacity, seat holds, checkout preparation, booking lifecycle and confirmations. Public pages, admin, partner widgets and AI.TEP are clients of this API; they do not implement booking rules themselves.
Shared live-tracking component - reuses the existing Leaflet/Supabase/OSRM work in customer view mode and admin manage mode.
Integration/event layer - payment, WhatsApp, email, analytics and future partner actions subscribe to booking/payment events instead of being buried inside booking logic.
Design direction: minimalist, high-end and boutique rather than generic 'tourist bus'. Use the existing deep red as the single accent color, with an off-white/charcoal base and strong photography.
2. Principles to hold throughout
API-first, but not microservices. Expose a clean booking API and domain boundaries, while keeping the first production system a modular monolith. Avoid unnecessary service sprawl.
One source of truth for booking rules. Availability, pricing, capacity, holds, payment state and confirmation logic live in the booking domain/API - never duplicated in frontend components.
Multi-operator ready. Every operator-owned core table carries operator_id and row-level security is scoped accordingly.
Products, not only tours. Support van_tour, boat_trip, attraction_ticket and future types. supplier_id distinguishes owned from resold inventory.
Orders and booking items. A single checkout may contain several products or quantities. Do not force one booking row to equal one product purchase.
Departures and inventory are explicit. Scheduled departures are separate from generic products. Capacity is enforced against a departure/inventory record.
Expiring seat holds are first-class. Seats must be temporarily reserved during checkout and released automatically if payment is not completed.
Payment records are separate from bookings. Store provider references, attempts, status transitions, refunds and webhook processing independently.
Events/outbox for integrations. Domain events such as booking.confirmed and payment.succeeded are persisted and delivered idempotently to integrations.
SEO fields are schema. Public content types carry slug, meta_title, meta_description and og_image; image alt text is required in the CMS.
Server-render public content. Use Next.js server rendering/ISR where appropriate for fast, crawlable public pages.
Protect existing search equity. Create and test redirects before cutover using the current indexed URL export.
Reuse the live map. Refactor existing Leaflet/Supabase/OSRM code rather than rebuilding tracking.
Auditability and permissions. Record sensitive admin changes and use clear roles/permissions rather than a single unrestricted admin.
Test the money-and-capacity paths. Automated tests are mandatory for capacity, simultaneous holds, webhook retries, cancellation/refund and RLS.

4. Production data model - v2
The original schema sketch is expanded here before production code is written. Exact columns can evolve, but these domain boundaries should remain.

Important modeling notes:
products describe what is sold; departures describe a scheduled instance of a product.
orders represent a checkout; booking_items let one checkout contain several products/quantities.
inventory_holds prevent overselling while a customer is paying. Holds expire automatically.
payments and payment_events are not fields on bookings; they have their own lifecycle and idempotency rules.
pricing_rules/capacity_rules may remain JSONB for product-specific flexibility, but critical searchable/reportable values should be normalized columns.
domain_events acts as an outbox: integrations consume persisted events safely and independently.
audit_logs records sensitive admin actions such as price/capacity changes, cancellations and permission changes.
5. Booking and payment state model
Booking / order flow
Search availability -> create expiring inventory hold -> create pending order -> start payment -> receive provider webhook -> mark payment paid -> atomically confirm booking/items and consume hold -> emit booking.confirmed -> send WhatsApp/email.
Recommended states
inventory_hold: active -> consumed | expired | releasedorder: pending -> awaiting_payment -> paid -> confirmed       -> cancelled | expired | partially_refunded | refundedpayment: pending -> processing -> paid -> failed -> partially_refunded -> refunded
The browser success redirect is never proof of payment. Provider webhooks are verified, idempotent and safely retryable. Capacity confirmation must be transactional so two concurrent customers cannot acquire the same final seat.
6. Event and integration architecture
Core booking logic emits persisted domain events. Integration handlers subscribe to those events; they do not sit inside the booking transaction.
inventory.held / inventory.expired
order.created
payment.succeeded / payment.failed / payment.refunded
booking.confirmed / booking.cancelled
customer.notification.requested
Use an outbox/retry pattern with idempotency keys. A WhatsApp or email outage must not roll back a paid booking; notification delivery can retry independently.
7. Security, roles and operational safeguards
Supabase Auth with explicit roles such as owner/admin, operations/staff and content editor; define permissions centrally.
RLS scoped by operator_id on operator-owned tables. Service-role credentials remain server-side only.
Public/customer clients never receive privileged database credentials and never write directly to booking/payment tables.
API keys are hashed, scoped, revocable and rate-limited; partner actions are attributable.
Audit sensitive admin changes. Preserve payment/provider event payloads according to a defined retention policy.
Use separate development/staging/production environments and protect production migrations.
Backups and a tested restore procedure are part of launch readiness, not a later enhancement.

9. SEO and answer-engine visibility
Treat SEO as a technical requirement and AEO/GEO as a content/discoverability strategy rather than a guaranteed ranking mechanism.
Write useful pages around real traveler questions and factual, extractable answers; keep marketing copy secondary to clear operational information.
Keep prices, schedules, stops and contact details consistent across the website and major third-party profiles.
Use server-rendered/indexable public content, semantic HTML, strong internal linking, canonical URLs, sitemap.xml and descriptive image alt text.
Use structured data only where it accurately represents visible page content. Validate markup and avoid assuming that schema guarantees rich results or AI citations.
Maintain genuine reviews and a clear source of truth for current operational information.
Periodically test how major search/answer products describe the business, but treat this as observational monitoring rather than a deterministic ranking metric.
10. Performance and observability
Keep public pages server-rendered/ISR where appropriate; minimize client JavaScript and lazy-load non-critical map/admin code.
Use responsive images and dedicated high-quality hero-image handling without unnecessarily serving original-size media.
Cache safe read-heavy endpoints such as public content; never cache customer-specific or rapidly changing availability incorrectly.
Add structured logs with request/order/booking identifiers so a failed checkout can be traced end to end.
Monitor frontend errors, API errors, webhook failures, slow database queries and booking conversion.
Define performance budgets for public pages and test mobile networks, not only desktop localhost.

13. Architectural guardrails - do not let an AI coding session violate these
Do not let public/admin React components implement their own availability, capacity or payment rules.
Do not let customer clients write directly to booking/payment/inventory tables.
Do not confirm bookings from a payment success page.
Do not remove operator_id/RLS because there is currently only one operator.
Do not replace the existing tracking stack without a demonstrated technical reason.
Do not create separate booking engines for van tours, boats, attractions or AI.TEP.
Do not introduce microservices, queues or infrastructure complexity merely because they are fashionable; introduce them only for a measured need.
Do not cut over from WordPress until redirects, sitemap, metadata and rollback are ready.
Do not trade away automated capacity/payment tests to meet a launch deadline.

14. Public website UX/UI blueprint
The public experience should feel like a premium digital guide to Shkodra with an exceptionally simple booking system, not a generic tour-bus or SaaS website. Before booking it is editorial, photographic and inspirational; after booking it becomes a practical travel companion. Core journey: Discover -> Understand -> Book -> Pay -> Ticket -> Track -> Explore.
14.1 Visual direction and design system
Authentic Shkodra photography is the dominant visual language; photography carries more weight than decorative illustration or icon grids.
Warm off-white base, charcoal text and the exact logo deep red as the single accent; #7A2020 remains only a working reference until sampled from the brand asset.
Use red for CTAs, active states, route markers and key numbers, not broad background washes.
Maximum two font families: elegant display typography for editorial headings and a highly legible sans-serif for UI.
Prefer whitespace and strong typography over excessive cards, borders, rounded corners and shadows.
Avoid autoplay carousels, stock tourism imagery, glassmorphism, decorative gradients, excessive animation and generic SaaS styling.
Animations must be subtle and functional; performance outranks decorative effects.
Mobile touch targets must be at least 44px and practical for one-handed use.
14.2 Desktop homepage structure
Header: Transparent over the hero initially, then a compact warm off-white sticky header. Navigation: Tour, Route, Explore Shkodra, Live Map, FAQ, language selector and deep-red Book Now CTA.
Hero: One exceptional Shkodra photo or restrained cinematic video, about 90-100vh. No carousel. Lead with “Discover Shkodra. Your way.”, short product explanation, Book Your Day and Track Live, then a compact factual line for price, daily ticket, destinations, audio guide and Wi-Fi.
Booking bar: Immediately after or slightly overlapping the hero. Ask only date, guests and departure. Preserve these selections throughout the booking flow.
Instant explanation: One ticket. One day. Shkodra at your pace. Show Hop On -> Explore -> Hop Back On and four concise facts: price, destinations, departure frequency and live tracking.
Interactive route: Make route + shared Leaflet map a centerpiece. Selecting a stop focuses the map and reveals photo, short description and useful operational information.
Destination storytelling: Large editorial photography for Shiroka, Rozafa Castle, Historic Centre and Mesi Bridge with short atmospheric copy and Discover links.
Live tracking: Signature feature with real mini-map, vehicle state, next stop/ETA only when reliable, and Open Live Map CTA.
How it works: Four steps: Buy one daily ticket; Hop on; Explore; Track and hop back on.
Today’s departures: Compact current timetable plus link to the full timetable; avoid a huge homepage table.
Reviews: A few genuine, source-attributed reviews and links to relevant third-party profiles.
Explore Shkodra: Editorial grid for high-intent destination content and real traveler questions.
More experiences: Optional at launch; later boat trips, attraction tickets, lake experiences, transfers and private tours use the same product architecture.
Final CTA: Strong Shkodra image, minimal emotional line and Book Your Day CTA.
Footer: Secondary navigation, contact/legal information, languages and social links.

14.4 Tour/product page
Open with strong title, concise value proposition, genuine rating/review source where available, key operational facts and visible price.
Desktop uses a sticky booking card; mobile uses the persistent booking action.
Recommended order: Route -> What is included -> Timetable -> Live map -> How it works -> Reviews -> FAQ.
Keep route, operating hours/frequency, audio-guide information, major attractions and boarding information easy to find.
Availability and price come from the Booking API; the page must not duplicate booking rules.
14.5 Mobile-first interaction model
Mobile shares the design system but has its own travel-companion interaction model rather than simply shrinking desktop.
Hero fills most of the first viewport with Book Your Day as primary and Track Live as secondary action.
After scroll, use a persistent bottom action bar with Live Van and Book/price; respect device safe areas and never cover content.
Booking opens as a focused bottom sheet or dedicated flow: date, guests, departure and clear total first, then details and payment.
Use a concise progress indicator: Selection -> Details -> Payment.
Never require re-entry of date, guest or departure selections.
Maps must be touch-friendly and must not unexpectedly steal page scrolling.
14.6 Post-purchase travel companion
The payment-success destination becomes “Your Shkodra Day”, not a generic thank-you page.
Prominent active ticket with product, guest count, validity date and QR/ticket action.
Live vehicle state and Track Van action when tracking is available.
Simple ordered journey/stops so the tourist understands the experience at a glance.
Immediate access to timetable, boarding point, route details and support.
Design for later PWA behavior and optional AI.TEP assistance without requiring a new customer experience.
14.7 Explore Shkodra content strategy
Use Explore Shkodra rather than a generic blog.
Build pages around real traveler questions, with a direct factual answer near the top and richer editorial content below.
Use authentic imagery, practical facts and internal links to relevant stops/products.
Launch-topic candidates: Shkodra in one day; visiting Rozafa Castle; Shiroka; Lake Shkodra; Shkodra to Theth; Shkodra to Koman; where to eat in Shkodra.
Source changing operational facts from structured platform data where possible so content does not drift.
14.8 UX guardrails
Do not hide price, route, frequency or booking CTA deep in the page.
Do not use a homepage carousel or several competing primary CTAs.
Do not put every section in rounded cards.
Do not use a generic template that could belong to any city or SaaS company.
Do not make Live Tracking a minor utility link.
Do not show live ETAs unless tracking data reliably supports them.
Do not overload the first booking step with unnecessary customer details.
Do not sacrifice Core Web Vitals for animation/map effects.
Do not hard-code changing price, schedule or route facts in multiple components.
