# Destinations and Calendar/Pricing audit and implementation plan

2026-09-25. Source: both user briefs supplied this turn. The operations attachment ends mid-example after section 26; the complete stated requirements through price snapshots are in scope.

Destinations currently live in seven fixed place.* fields per attraction in content_pages/website-homepage, plus four optional plain-text explore-* guide records. Public consumers enumerate a static four-item array. Reuse content_pages draft/published_body, SEO and storage; migrate existing card and guide data into individually owned destination records, retaining raw legacy bodies and old links. Archive only; no operational deletion. Dynamic readers drive all destination consumers and the sitemap. Per-destination editor replaces both duplicate fixed fields and guide editors.

Operational Stop means the independent live map's published feature with properties.objectId; local stops table is historical/inactive. Do not substitute GeoJSON array indices for stable IDs. Read the map's published stops for an optional external reference; do not copy or mutate GPS/geofences/ETA. Terminology audit stored in private/destination-terminology-audit.txt. Local map-preview/position code, stops tables, stop detection, stop numbering and map controls remain operational terminology. Editorial route previews and destination CMS use Destination.

Operations currently has one service_schedules row per product and schedule_exceptions per day. effective_schedule_times_v1 resolves dated times; materialize_service_date_v1 and read_availability_v1 generate requested-day departure inventory, guarded by advisory and row locks. Holds and confirmed booking_items consume quantity seats. Product pricing_rules has one EUR per-guest amount. Pending orders snapshot price and confirmed orders never reprice. No Adult/Child/Infant, range-price rules or generic booking-modification endpoint exists. Existing schedule saves guard capacity/history, but closing a booked departure currently rejects; implement explicit confirmed closure without deleting bookings, retaining locks and blocking new sales.

Plan: (1) dynamic destinations migration, editor, readers, URL preservation and tests; (2) extend authoritative product pricing and existing schedule exception hierarchy with category configuration/range overrides, then shared effective quote and passenger snapshots on holds/items; (3) month calendar/date-range/day editor and standard pricing, move old inventory UI under Advanced; (4) public/admin passenger selectors and server adult validation, historical-price/notification/QR compatibility; (5) migrations, isolated regression/concurrency tests and browser checks. Preserve current prices by migrating existing per-guest price to Adult; other categories require explicit owner pricing, no example prices. All physical passengers count as seats. No production deployment or outbound email enablement.
