Local browser network checks on `/`, `/route`, `/your-day`, `/live`, and `/book` saw no Netlify or Mapbox requests or iframe origin warnings. The local homepage lacked hosted CMS data. Its enabled stop-section behavior was separately exercised by the DOM test. |
| Initial load, disconnection and new map publications | Fixed locally | `route-tracking/route.ts` returns geometry alongside status when the client version differs. `route-explorer.tsx` retries on reconnect and on request, adopts geometry and status together, rejects a prior version and preserves a selected ID and manual camera position where possible. If a selected item disappears the itinerary returns. Chromium confirmed initial failure then Retry, online refresh, version change, retained selection and rejection of an older version at 390 and 1440 px. The read model withholds live status and ETA if the snapshot identifies a different map version. |

## Release and rollback

The Web App change is compatible with the existing public tracking schema and needs no migration, provider credentials, scheduler change, or new Vercel variable. Keep the previous Vercel release and its Mapbox configuration available for rollback until acceptance. Before any production release, run authenticated editing in an isolated Web App and tracking Supabase pair, including unpublished draft, published geometry and POI, hours, seasonal copy, booking activation and calendar rollback. Record the website publication cache invalidation and the Route tab’s roughly ten-second polling cadence. Verify direct booking entry and one booking per intended action with isolated recipients before checking delivery.

The Audioguide change has no storage migration and keeps the cue field optional. Roll back the Audioguide Worker and browser bundle together. Keep existing published versions and issued QR/media links available. Locate the deployed GPS processor, scheduler receipt and service state through read-only production access before changing any tracking infrastructure.
