# Phase 3E booking operations

Implemented staff booking workspace with recent orders, departure-date filtering, exact customer-email lookup, contact/item/booking details, manual unpaid booking creation and reasoned cancellation. Payment details are read only for owner/admin roles; operations cannot access raw payment records. Content editors cannot access the workspace. Reads use authenticated RLS and explicit operator scopes; actions reauthorize on each request.

Manual creation calls the new create_staff_booking_v1 service-only RPC, which validates active owner/admin/operations membership and invokes existing create_hold_v1, create_pending_order_v1 and prepare_booking_v1 functions in one transaction. It derives its private session internally and records staff-attributed booking.staff_created event/audit data. Invalid customer/pricing/availability rolls back the entire operation. Request UUIDs make concurrent submissions idempotent; error redirects preserve the retry UUID. Staff must retry the same details, or a conflict is expected. No manual price, paid-state or capacity override exists.

Manual bookings remain pending with awaiting_payment orders and time-limited holds. There is no cash/payment collection or indefinite seat reservation in this phase. Price/capacity must already be explicitly configured through the V1 booking contract; publishing a product alone is insufficient. Pending orders can outlive their expired holds and must not be mistaken for confirmed inventory. Current operational UI shows order/booking states; automated order-expiry reconciliation remains future work.

Cancellation calls the existing cancelOrder domain adapter with confirmation and a required reason. Paid orders emit refund-review requests; no provider refund or payment success can be recorded through these forms. Direct refund execution stays disconnected until the payment phase.

Lists are bounded to 100 orders/upcoming departures, 100 customer matches and 1,000 date-filter departures/items. This is a date-filtered list rather than a graphical calendar. Existing customer lookup is read-only; manual booking captures a new per-order customer record, consistent with the domain. Customer fields are not put in mutation redirect URLs. Customer email search uses GET, so staff should avoid sharing search URLs.

Native PostgreSQL tests prove invalid customer rollback leaves no hold, forged actor denial, concurrent duplicate creation returns one booking, server-computed total, unpaid status/no payment insertion and one staff audit entry. Existing cancellation/confirmation/RLS tests remain applicable. Visual and interactive browser QA plus owner onboarding are still pending. No new environment settings or production changes. Next: Phase 3F admin usability/mobile QA, then Phase 3 audit.

Results: npm test passed 95 tests (13 identity/navigation, 5 adapter, 63 embedded database, 14 native PostgreSQL). Lint/typecheck/build passed. CLI dry-run selected only the manual-booking migration and development push succeeded. Hosted Auth/local HTTP verifier rendered the authorized booking page and confirmed role/tenant restrictions; temporary identities were removed. It did not submit a real customer booking. The final UI also displays stored hold status and expiry without exposing session keys; typecheck/lint were rerun after that display addition.
